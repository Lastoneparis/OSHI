# OSHI-branded Meshtastic firmware

Meshtastic builds that show the OSHI mark at boot instead of the Meshtastic
logo, served from the flasher alongside the stock images.

## What is actually changed

Three files. Nothing in upstream source is patched:

```
variants/esp32s3/heltec_v3/variant.h
variants/esp32s3/tlora_t3s3_v1/variant.h
variants/esp32s3/rak_wismesh_tap_v2/variant.h
```

Each gains a `USERPREFS_OEM_*` block. **This is Meshtastic's own whitelabel
hook** — the same one the in-tree `muzi_base` variant uses — not a patch of the
stock splash. That matters for maintenance: a firmware bump merges cleanly
instead of conflicting in `Screen.cpp` every time upstream touches the boot
sequence.

The full diff is in `oshi-branding.patch`, taken against upstream `08722da`.

## The logo

`tools/oshi_boot_logo.py` draws it and packs it to XBM in one step; the output
is `oem_logo.h` and a 3× preview.

It is DRAWN for 128×64 monochrome, not downscaled from the app icon — at 1 bit
per pixel a resized logo turns to mush. Two failures were caught by looking at
the preview rather than trusting the code: the "I" fell off the right edge, then
the wordmark collided with the ring. The script now measures the text and places
it, and refuses to overflow.

## WisMesh Tap v2 takes a different route

`USERPREFS_OEM_IMAGE_DATA` is read by exactly two display paths — OLED
(`graphics/draw/UIRenderer.cpp`) and E-Ink (`InkHUD/.../LogoApplet.cpp`). The
WisMesh Tap v2 has a **colour TFT with a touch panel** (LGFX, FT5x06), so the
XBM block compiles on that variant but displays nothing there — it is left in
place only so the file matches the other two.

A TFT boot logo instead comes from `branding/logo_<width>x<height>.png` in the
firmware repo (`oshi-mesh-firmware`, not this one), copied into the filesystem
image by that repo's `bin/platformio-custom.py`. For the WisMesh Tap v2's
320×240 landscape panel that file is `branding/logo_320x240.png`, generated by
`branding/make_tft_boot_logo.py` there — the colour counterpart of this
directory's `oshi_boot_logo.py`, drawn as geometry at the panel's exact pixel
size for the same reason the OLED one is.

Heltec V3 and LILYGO T3-S3 are both SSD1306 OLED and behave identically.

## Building

```sh
python3 -m venv piovenv          # PlatformIO needs Python 3.10+
./piovenv/bin/pip install platformio
./piovenv/bin/pio run -e heltec-v3
./piovenv/bin/pio run -e tlora-t3s3-v1
```

Build ONE target at a time. Two concurrent `pio run` invocations race on the
shared toolchain download and the second dies with
`Missing framework-arduinoespressif32-libs package` — a failure that looks like
a broken build and is only a download collision.

Verify the branding reached the binary, not just the source:

```sh
strings .pio/build/heltec-v3/firmware-heltec-v3-*.bin | grep -c OSHI   # ≥ 1
```

## Publishing

`tools/publish_firmware.py` stages each build as `oshi-<target>/` beside the
stock directory and rsyncs it to `/var/www/oshi/lora/firmware/`. The stock builds
are untouched, so flashing upstream firmware keeps working.

md5 and byte counts in the manifest are computed from the files on disk, never
copied from the stock manifest. A manifest describing different bytes than the
ones served is the failure that presents as a corrupt flash and cannot be
diagnosed from a browser.

Verified after upload by re-hashing the served files against their own manifest:
4/4 match for both targets.

## Licence

Meshtastic firmware is **GPL-3.0**. Distributing a modified binary obliges us to
make the corresponding source available. That is what `oshi-branding.patch` plus
the upstream commit hash in this file are for, and why each generated manifest
carries `"repo"` pointing at the fork rather than at `meshtastic/firmware` —
someone holding one of these binaries can find the source that produced it.
